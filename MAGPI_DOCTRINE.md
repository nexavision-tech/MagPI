# 🧭 The MagPI Doctrine

Welcome to the **MagPI (Magnetic & Planetary Integrations)** Doctrine. 

This document serves as the official standard operating procedure (SOP) and semantic guidebook for the MagPI ecosystem. It is intended for geospatial developers, data scientists, and community contributors to understand the established "givens" of the platform.

---

## 🎨 1. Visual Taxonomy & Color Semantics

To reduce cognitive load during visual programming, MagPI strictly enforces a semantic color palette. 

### 1.1 Node Categories (Background Colors)
Nodes are grouped by their functional domain. If you are developing a community node, you must adhere to the following category colors:

*   🌐 **Cyan (`bg-cyan-700`) - Open Data WFS:** External data ingestion, web feature services, and sovereign data APIs (e.g., Copernicus, USGS, NLCD).
*   🛰️ **Emerald (`bg-emerald-600`) - Image Analyst:** Classical remote sensing operations (NDVI, Pansharpening, Reclassification).
*   ⚙️ **Blue (`bg-blue-600`) - Core Primitives:** Foundational system operations (Loading existing rasters/vectors from disk, creating feature classes).
*   🛠️ **Orange (`bg-orange-600`) - Management & Conversion:** Geometry manipulations, clipping, buffering, and array indexing.
*   🧠 **Purple (`bg-purple-600`) - GeoAI / Deep Learning:** Advanced AI workflows (Training models, Object Detection, Generative AI).
*   🔀 **Amber (`bg-amber-600`) - Logic & Flow:** Workflow controllers, looping, and boolean decision matrices.
*   📈 **Rose (`bg-rose-600`) - Spatial Statistics:** Zonal statistics, volumetric analysis, and academic/scientific verification algorithms.

### 1.2 Data Flows (Ports & Wires)
Data types passed between nodes are strictly typed and color-coded. A port will only accept a connection from a matching type.

*   🔵 **Blue (`#5ac8fa`) - Raster Data:** Imagery, Digital Elevation Models (DEMs), Synthetic Aperture Radar (SAR), multi-dimensional tensors, and pixel-based predictions.
*   🟢 **Green (`#32d74b`) - Vector Data:** Polygons, lines, points, GeoJSON footprints, truth labels, and spatial intersections.
*   🟡 **Yellow (`#ffcc00`) - Constants & Extents:** Spatial Areas of Interest (AOI / Bounding Boxes), dates, float/integer constants, and mathematical variables.
*   🟣 **Purple (`#bf5af2`) - Metadata:** JSON payloads, operational status reports, and execution logs.

## 🌍 2. Data Ingestion Philosophy

MagPI supports two primary methods for establishing a geographical area of analysis. It is critical to understand when to use which method.

### 2.1 The Implicit AOI (Drawing)
**Node:** `Spatial Extent (AOI)`
*   **Usage:** Best for rapid prototyping, ad-hoc analysis, and broad sovereign data pulls (e.g., fetching all Sentinel-2 tiles over a city).
*   **Mechanism:** The user physically draws a bounding box on the 2D/3D viewport. The coordinates are injected into the pipeline as a primitive Yellow variable (`EXTENT`).

### 2.2 The Explicit AOI (Importing)
**Node:** `Input Vector` (or dropping an ENVI ROI `.xml` into the workspace)
*   **Usage:** Mandatory for structured operational workflows, academic reproducibility, or when analyzing specific fragmented topologies (e.g., assessing damage against a pre-existing catalog of building footprints).
*   **Mechanism:** A `.geojson`, `.shp`, or `.xml` file is loaded directly from disk. The output is a Green `VECTOR` stream, which contains exact geometry (often used downstream for masking or zonal statistics) rather than just a bounding box.

## 🏛️ 3. Fundamental "Givens" (System Rules)

1.  **Universal Projections & Datums:** To ensure seamless visual rendering on the 3D Cesium globe and 2D Leaflet canvas without on-the-fly reprojection thrashing, all data generated by MagPI is standardized:
    *   **Horizontal Datum:** WGS 84 (`EPSG:4326`) is the mandatory default for all geometric outputs.
    *   **Vertical Datum:** `EPSG:3855` (EGM2008 / NAVD88 equivalent for Cesium) is the standard for 3D elevations and volumetric calculations.
2.  **Attributions & Bibliography:** Any community node performing a complex derived scientific calculation (e.g., Structural Damage Volume, GLCM Textures) **MUST** include an academic citation. 
    *   Citations are strictly decoupled from the node source code to prevent link rot. 
    *   Developers must define a `reference_keys` array in their node metadata and map the keys to the master `/magpi_workspace/academic_references.json` registry. This serves as MagPI's centralized bibliography.
3.  **Vectorized First:** MagPI is an escape pod from legacy loop-based GIS (like old `arcpy.da.SearchCursor` scripts). All translation implementations **must** prioritize vectorized array operations via `numpy`, `scipy`, or `pandas`. Iterating row-by-row over a dataset is considered a failure of implementation.
4.  **Airflow Compatibility:** All node execution logic must be self-contained so that the `airflowGen.js` compiler can safely wrap the node instantiation within an isolated Airflow `@task` decorator for enterprise execution.

## ⚖️ 4. Disclaimers & Analyst Responsibility

MagPI is designed to rapidly ingest massive quantities of open-source and sovereign data (e.g., UNOSAT Damage Assessments, MRLC NLCD, USGS 3DEP). However, **speed does not replace rigor**.

*   **Accuracy Verification:** The MagPI execution engine assumes that incoming datasets are accurate. Users are strictly responsible for verifying the accuracy, spatial resolution, and temporal currency of the data they ingest.
*   **Volumetric Errors:** When performing operations like `Structural Damage (Volume)`, be aware that utilizing low-resolution optical shadows instead of high-res LiDAR will introduce significant margins of error in height estimations.
*   **Coordinate Thrashing:** While the internal UI enforces EPSG:4326 for rendering, analysts must verify that their input files (.shp, .gdb, .geojson) are projecting properly in the translation matrix, especially when fusing disparate sovereign datasets.
